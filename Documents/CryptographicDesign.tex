\section{Introduction}
This document specifies the cryptographic technique used by the Privacy Preserving Data Analytics Engine (E-Privacy) to compute over sensitive data \emph{while it is being processed}, without ever exposing plaintext to the compute nodes. Conventional pipelines decrypt data before computation, creating a plaintext-exposure gap at the point of processing; this design closes that gap using homomorphic encryption.

\subsection{Assumptions}
\begin{itemize}[leftmargin=1.5em]
    \item[B1.] Parties use standard, well-reviewed cryptographic libraries rather than custom primitive implementations.
    \item[B2.] The Data Owner's Paillier private key is generated using a cryptographically secure random number generator.
    \item[B3.] The 2048-bit Paillier key length is the default operating point, per the empirical trade-off analysis in Section~\ref{sec:empirical}: it gives sub-5-minute aggregation latency for a 2M-record batch, versus 3072-bit's disproportionate latency cost.
\end{itemize}

\section{Homomorphic Computation over Ciphertext}
We use the \textbf{Paillier cryptosystem}, a partially homomorphic public-key scheme, with a \textbf{2048-bit modulus $n$} and a probabilistic, randomized encryption of each plaintext value, to ensure confidentiality of the data \emph{while it is being processed} by the untrusted compute nodes that run the aggregation query. Paillier is applied directly to the sum, average, and count operations the Engine performs; no other cipher or mode is required for this stage, since the compute node only ever operates on ciphertext. Its two essential properties are the additive homomorphism and the affine (scalar-multiplication) property:
\[
E(m_1) \cdot E(m_2) = E(m_1 + m_2) \bmod n^2, \qquad E(m)^k = E(km) \bmod n^2.
\]
These let the compute engine sum and scale encrypted values without decrypting them, so the plaintext is never reconstructed on the server performing the computation -- the plaintext-exposure gap that conventional decrypt-then-compute pipelines leave open at the processing stage.

\subsection{Key Management for Processing}
\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Keypair generation:} the Data Owner generates a Paillier keypair locally from two large random primes $p, q$, giving modulus $n = pq$ (default 2048 bits, per B3). The public key $(n, g)$ is given to the compute engine to encrypt inputs and combine ciphertexts; the private key $(\lambda, \mu)$ never leaves the Data Owner and is used only to decrypt final aggregate results.
    \item \textbf{Key rotation:} keypairs are rotated per analytics campaign, so a compromised key exposes only that campaign's results, not the full processing history.
\end{itemize}

\subsection{Why Paillier over Alternatives}
RSA-based decrypt-compute-re-encrypt requires the server to hold plaintext mid-computation, violating the processing-confidentiality requirement outright. Fully Homomorphic Encryption (FHE/CKKS) avoids this too, and additionally supports multiplication between ciphertexts, but at a storage and latency cost that is disproportionate for additive aggregation workloads (Section~\ref{sec:empirical}). Paillier is chosen as the narrowest scheme that still closes the plaintext-exposure gap for the sum/average/count operations this engine performs.

\section{Empirical Justification}
\label{sec:empirical}
Four candidate approaches were benchmarked on a 2,000,000-record dataset: \textbf{Plaintext} (baseline), \textbf{RSA} (decrypt-compute-re-encrypt), \textbf{PHE/Paillier}, and \textbf{FHE/CKKS}, across 1024/2048/3072-bit key lengths.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Storage:} FHE ciphertext expansion is impractical for tabular aggregation, while PHE stays within an $\sim$6--16x expansion over plaintext at all tested key lengths.
\end{itemize}

\begin{itemize}[leftmargin=1.5em]

\end{itemize}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Decision:} PHE (Paillier) at a 2048-bit modulus gives the best combination of processing confidentiality, storage cost, and query latency for additive aggregation. FHE is retained as a pluggable future option only if a workload requires ciphertext-ciphertext multiplication.
\end{itemize}

\section{Conclusion}
Paillier at a 2048-bit modulus lets the Engine compute sums, averages, and counts directly over ciphertext, eliminating the plaintext-exposure gap that conventional decrypt-then-compute pipelines leave at the processing stage. This is achieved with acceptable storage overhead and query latency, as confirmed by empirical benchmarking against RSA and FHE alternatives.
